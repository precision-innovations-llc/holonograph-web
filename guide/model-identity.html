Chapter 17

Model identity

The model you asked for and the model that answered are two different facts. A vendor can re-route behind an unchanged alias. Holonograph records both sides, so that change has a name instead of showing up as unexplained drift.

What it is

Two apparatus-owned axes, stamped by the SDK at emit time:

ColumnWhat it records
light_source_identifierThe light source that was requested.
light_source_served_modelThe model the vendor actually served.

Both sit in a reserved namespace. The apparatus owns them, and a consumer may not declare a substrate column under that prefix. A declaration that collides is rejected at boot rather than silently shadowed.

Why it matters

An alias is a promise about identity that the vendor is free to reinterpret. When a provider moves the model behind a name you did not change, every reading on that surface shifts at once. With only the requested axis recorded, the shift has no cause attached to it and reads as a substrate or lens problem.

Served model is a first-class axis, so the transition is a recorded fact. The served-model ledger reports those transitions over a window. Two properties of that ledger matter when you read it: the changepoint penalty scales with the number of models in the window, and a stray served model raises an explicit excursion rather than widening the band until the stray fits inside it.

How to use it

  • Nothing to configure on the happy path. The client carries light.servedModel to the wire.
  • In HTTP mode the attested servedModel and keyId ride on the primary record.light.
  • If an older client did not send the axis, the server recovers it at ingest, so capture does not depend on client version.
  • For history captured before the axis existed, an operator-run backfill resolver and its CLI fill it in.

Reading the output

A surface whose requested identifier held steady while the served model moved is a light-source change, not a substrate change. Drift attribution reads both axes, so that case resolves to the light source instead of competing with your own releases for the explanation.

Reference

The judge has the same two sides

The judge lens carries its own requested provider and credential identity, authored by the apparatus and treated as a judge drift source. A single lensVersion under-specifies a judge: two judges scoring the same response under the same software but a different rubric, a different served model, or a different input-context scope are different lenses. The judge-lens facets are stamped on every scored event under the reserved judge. namespace.
