Chapter 19

On-demand multiplex runs

POST /lens/multiplex/run takes one request and fans it across several vendors now, so a cross-vendor comparison exists on demand rather than only where multiplex routing happened to be on.

What it is

Three ways to name the request to fan out:

  • sourceEventId: replay this exact event's captured request. The event must carry light.rawRequest.
  • sourceCorrelationId: resolve the first event under this correlation that carries a request.
  • input: a direct canonical request body. The cold-start path, with no captured source event, so a comparison need not wait for the multiplexer to have run once. Requires targetSurfaceId.

The peers are primaryless

In the served multiplex one result is returned and the rest are observers. Here every peer is returned equally and none can substitute for another. The primary and observer privilege does not apply, so no vendor is the authoritative answer by position.

Why it matters

persist (default false) turns an ephemeral comparison into a durable collection. Each peer is written as an immutable, provenance-bucketed event outside the production trajectory, idempotent on (groupId, vendorId). Re-posting the same groupId and vendor list re-runs only the peers not already collected, so a resume never double-charges and never double-records.

That makes a persisted run usable as a scientific collection. A study controller supplies its own cell identity in groupId, for example a specimen, replicate and wave key, and the collection resumes cleanly across interruptions.

A failed peer is an observation

A peer that errors is recorded as its own event kind, carrying the vendor reason, its class, and that peer's effective vendor options. It is the channel-availability trail and it is never compacted. Observation and scoring consumers do not read it. An errored peer is never silence.

How to use it

  • Name the request, name the vendors, name who triggered it.
  • The run is cost and approver gated. A run whose estimate exceeds the threshold requires acknowledgedEstimateUsd.
  • Set persist and a groupId when the comparison is evidence rather than a look.

Reading the output

Each leg carries its vendor, its result, its stopReason and the providerRequestId, and those also reach the light snapshot. Each peer's effective vendor options are persisted on its own light.rawRequest, so a per-peer option difference is visible rather than inferred.

One boundary on scoring

Scoring is instrument-identity-bound. The binary does not run the operator's judge. The single exception is a surface's gated dimensions, which the gate executor scores inline to decide flag, block or retry. A leg's dimensions[] therefore carries only the gated-dimension verdicts that fired for that run mode, and not a full grading.

Reference

  • POST /lens/multiplex/run
  • Peers share correlation id multiplex:<groupId>.
  • Each peer's event id derives deterministically from (groupId, vendorId).
